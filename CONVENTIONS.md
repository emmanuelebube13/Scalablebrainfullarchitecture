# Scalable Brain Hub — Site Conventions

> **Audience:** Any agent or human adding or modifying content in this repository.
> This document tells you where things go, what shape they must take, and how to verify
> that what you wrote is correct — without reading the source code.

---

## 0. The one rule

**Content lives in `data/`. Presentation lives in `assets/`.** An agent updating a status,
adding a task, documenting a pipeline stage, or adding a new system should only ever touch
`data/` (and `templates/` when adding a system). If your change requires editing HTML, CSS
or JavaScript, you are making a design change, not a content change. Those are different
problems with different reviewers.

---

## 1. Repository layout

```
data/
├── registry.json            Project identity, principles, and the list of systems
├── architecture.json        Nodes, edges and traceable flows for the unified map
├── decisions.json           Architecture decision records — including open ones
├── goals.json               Milestone ladder, goals, dependency matrix, task tracker
└── systems/
    ├── system-1.json        One file per subsystem
    ├── system-2.json
    ├── system-3.json
    └── _TEMPLATE.json       Copy this to add System N (do not edit this file as content)

schema/                      JSON Schema for each file in data/ — update alongside the data
templates/
└── system.template.json     Canonical template for a new system (same as data/systems/_TEMPLATE.json)
tools/validate.mjs           Zero-dependency validator: node tools/validate.mjs
assets/
├── css/main.css             Single stylesheet for all pages
├── css/goals.css            Goals-specific styles (goals.html only)
└── js/                      ES modules, one per page, plus core.js and search.js shared
CONVENTIONS.md               This file
```

**One file to rule them all for systems:** each system is fully described in
`data/systems/system-N.json`. Nothing about a system's identity, status or structure
lives anywhere else in the data layer.

## 2. File shapes at a glance

### 2.1 `data/registry.json`

Top-level keys:
- `schema_version` (string)
- `project` — name, subtitle, thesis, principles, `as_of`, repository URLs
- `systems[]` — `{id, ordinal, file}` — one entry per system; all pages load systems from here
- `status_vocabulary` — the allowed values for `system.status.state`
- `decisions_file`, `goals_file`, `architecture_file`

To add System 4: append `{"id": "system-4", "ordinal": 4, "file": "data/systems/system-4.json"}`
to the `systems` array. **Do not change `ordinal` of existing systems.**

### 2.2 `data/systems/system-N.json`

**Required fields:** `schema_version`, `id`, `ordinal`, `name`, `status`, `summary`, `sections`

**Required sections (all six must be present, in any order):**

| Section id    | `kind`        | Purpose |
|---------------|---------------|---------|
| `ingestion`   | `ingestion`   | Data sources, formats, transformation, feature engineering |
| `core-logic`  | `pipeline`    | Strategy mechanics, decision logic, execution parameters |
| `interfaces`  | `interfaces`  | Published contracts, transports, consumers |
| `operations`  | `operations`  | Deploy procedure, restart, backup, monitoring |
| `state`       | `state`       | State machine, configuration parameters, feature flags |
| `open`        | `issues`      | Known gaps. Uses `issues[]`, not `body` |

A section that has no content yet must still be present as an empty shell:
```json
{ "id": "operations", "title": "Operations", "kind": "operations" }
```
The renderer shows "not yet documented" for empty sections — **that is the correct
behaviour**. An empty section and a missing section must look different. Never omit a
section because it has no content.

**Section content keys** (all optional on any section):

| Key | Shape | Renders as |
|-----|-------|-----------|
| `body` | `{technical: [], plain: []}` | Paragraphs, one array per voice |
| `stages[]` | `{code, name, module, output, technical, plain}` | Numbered pipeline list |
| `tables[]` | `{title, columns, rows, note}` | Scrollable table |
| `callouts[]` | `{tone, title, technical, plain}` — `tone` ∈ `good/info/warn/bad` | Highlighted box |
| `issues[]` | `{id, severity, title, text}` — `severity` ∈ `high/med/low` | Known-gaps list |

**`kind` vocabulary (closed set):** `ingestion`, `pipeline`, `interfaces`, `operations`,
`state`, `issues`, `evidence`. Using a value outside this set generates a validator warning.

### 2.3 `data/architecture.json`

| Key | Shape | Notes |
|-----|-------|-------|
| `columns[]` | `{id, title, system, subtitle}` | Left-to-right lanes. `system` tints the lane |
| `nodes[]` | `{id, column, row, label, kind, status, detail}` | `row` may be fractional |
| `edges[]` | `{id, from, to, label, kind, status}` | `kind` ∈ data/artifact/message/order/control |
| `flows[]` | `{id, name, edges[], technical, plain}` | Traceable path. `edges` are edge ids |
| `legend` | `{kinds[], statuses[]}` | Labels for the legend under the map |

`status` on both nodes and edges: `live`, `degraded`, `blocked`, `planned`. Anything other
than `live` is drawn dashed — the map cannot flatter a broken link.

### 2.4 `data/goals.json`

| Key | Shape |
|-----|-------|
| `milestones[]` | `{id, name, state, date, summary, plain, falsifier}` |
| `goals[]` | `{id, title, kind, horizon, period, status, metric, why, plain, definition_of_done, dependencies[], blocked_by}` |
| `goals[].metric` | `{name, current, target, unit, note}` |
| `goals[].dependencies[]` | `{system, role, need}` — `role` ∈ owner/required/consumer/none |
| `tasks[]` | `{id, system, goal, period, status, priority, urgency, title, detail, evidence}` |

A task whose `goal` or `system` does not resolve is a validation **error**, not a rendering
quirk — `node tools/validate.mjs` catches it.

### 2.5 `data/decisions.json`

| Key | Shape |
|-----|-------|
| `id`, `title`, `date`, `source` | string. `source` points at the authoritative doc |
| `status` | `proposed` or `accepted` |
| `problem`, `argument`, `decision`, `load_bearing_requirement` | `{technical, plain}` |
| `consequences` | `{good: [], bad: []}` — both sides; omitting costs is not allowed |
| `transition[]` | `{step, text}` |
| `open_questions[]` | `string[]` |

## 3. Writing content — two invariants

### 3.1 Every explanation comes in two voices

Anywhere the schema allows an explanation, it takes `{technical, plain}`. The header toggle
picks one. Writing only `technical` is allowed and falls back gracefully — but the `plain`
version is where most of the value is, because it is the version a non-engineer can challenge.

```json
"summary": {
  "technical": "4-state Gaussian HMM on D1/H4/H1 with K-Means fallback below a 0.70 accuracy gate.",
  "plain": "Sorts market history into four kinds of weather, and falls back to a simpler method if it cannot do that reliably."
}
```

### 3.2 Light inline markup — not Markdown

JSON strings support: `` `code` ``, `**bold**`, `*italic*`, and `[label](https://…)`.
Everything is HTML-escaped first, so agent-authored content cannot inject markup.
Use `tables[]` for tabular data, not hand-drawn ASCII.

### 3.3 Never invent content

Do not fabricate thresholds, statuses, dates, or numbers. If a field has no value, leave it
absent or write the empty-section shell. A confident wrong number on a live trading system
page is the worst available outcome. List content gaps in your commit message and handoff.

## 4. How search picks content up

`assets/js/search.js` builds a full-text index at page load over:

- **Architecture nodes** — `label`, `detail.technical`, `detail.plain`, `kind`, column title
- **Architecture edges** — `label`, from/to node labels
- **Systems** — `name`, `role`, `summary.technical`, `summary.plain`
- **System sections** — `title`, all `body`, `stages`, `tables`, `callouts` and `issues` text
- **Goals** — `id`, `title`, `why`, `plain`, `definition_of_done`
- **Tasks** — `id`, `title`, `detail`, `goal`
- **Milestones** — `id`, `name`, `summary`, `plain`
- **Decisions** — `id`, `title`, `problem.technical`, `decision.technical`
- **Runbook headings** — heading text + next 3 non-heading lines as snippet

**For new content to appear in search results, it needs no special registration.** The index
is rebuilt from the data files on every page load. Adding text to a system section, a task,
or a decision makes it searchable automatically.

Each result links directly to the item: system sections link to `system.html?id=X#section-id`,
runbook headings link to `runbook.html#slug`, etc.

## 5. How to add a new system (System 4, 5, N)

Follow these steps exactly. You should not need to read source code.

### Step 1 — Copy the template

```
cp templates/system.template.json data/systems/system-4.json
```

(On Windows: `copy templates\system.template.json data\systems\system-4.json`)

### Step 2 — Fill in the required fields

Open `data/systems/system-4.json`. Set:
- `"id": "system-4"` (matches the filename)
- `"ordinal": 4` (next integer after the last system)
- `"name": "The …"` — give it a short name
- `"role"` — one line describing its job
- `"host"` — where it runs
- `"duty_cycle"` — when it runs
- `"accent"` — a 6-digit hex colour, e.g. `"#c084fc"`
- `"status.state"` — must be one of the keys in `registry.status_vocabulary`
- `"status.as_of"` — today's date in `YYYY-MM-DD`
- `"summary.technical"` and `"summary.plain"`

For sections with no content yet, leave the empty shell. Do not delete any of the six
required sections.

### Step 3 — Register it

In `data/registry.json`, append to the `systems` array:
```json
{ "id": "system-4", "ordinal": 4, "file": "data/systems/system-4.json" }
```

### Step 4 — Put it on the map

In `data/architecture.json`:
1. Add a column to `columns`:
```json
{
  "id": "s4",
  "title": "System 4 — The Analyst",
  "system": "system-4",
  "subtitle": "Computer 4 · nightly"
}
```
2. Add at least one node that references the column:
```json
{
  "id": "s4-report",
  "column": "s4",
  "row": 2,
  "label": "Report builder",
  "kind": "process",
  "status": "planned",
  "detail": { "technical": "…", "plain": "…" }
}
```
Note: `row` numbers are relative; the map places nodes automatically.

### Step 5 — Wire goal dependencies (if relevant)

For any goal in `data/goals.json` that System 4 touches, add a dependency entry:
```json
{ "system": "system-4", "role": "owner", "need": "What System 4 provides" }
```
Role options: `owner` (builds it), `required` (depends on it), `consumer` (uses it), `none`.

### Step 6 — Add it to search

Nothing to do — `search.js` picks it up automatically from the data files.

### Step 7 — Validate

```
node tools/validate.mjs
```

Expected: `OK — N warning(s)` where the warnings are for empty sections
("`missing content`"). Zero errors is required. Fix any errors before committing.

### Step 8 — Verify

Serve locally (`python3 -m http.server 8080`) and check:
- The home page shows a System 4 card
- `system.html?id=system-4` loads and shows the hero and tabs
- `architecture.html` shows the new column with the node(s)
- The nav "Systems" link on any page still works (it links to `system.html?id=system-1`;
  the hero shows all systems including the new one)
- Press `/` on any page, type "system-4" or the system's name — it appears in search results

### Step 9 — Commit and push

```
git add data/registry.json data/systems/system-4.json data/architecture.json
git commit -m "Add System 4 — <The Name>"
git push
```

## 6. CSS conventions

All styles live in `assets/css/main.css` (global) or `assets/css/goals.css` (goals page only).
There is no build step; what is in those files is what ships.

**Where to add a new rule:**

| What you are styling | Where |
|----------------------|-------|
| A new page-level component | Bottom of `main.css`, after the last relevant section |
| A modification to an existing component | Near the existing rule for that component |
| Goals-page-only styles | `goals.css` |
| Search overlay, map controls, runbook ToC | Already in `main.css` — find the comment block |

**Do not add inline `<style>` blocks to HTML files.** The operations page has legacy inline
styles that predate this convention; they should eventually be moved.

**CSS variables** (from `:root`): use `var(--accent)`, `var(--good)`, `var(--warn)`,
`var(--bad)`, `var(--info)`, `var(--muted)` for semantic colour. Use `var(--s1)`,
`var(--s2)`, `var(--s3)` for per-system accent colours. Both light and dark themes are
defined in `:root` and `[data-theme="light"]` respectively — any colour you add must have
entries in both.

For text sitting **on** an accent-coloured background use `var(--on-accent)`, never a
literal `#fff`: dark mode's accent is a bright amber that white text fails against, and
light mode's is a deep ochre that needs light text. The token flips with the theme.

**Typography variables**: `var(--font-display)` (Instrument Serif, used italic for `h1`
and `h2`), `var(--sans)` (Space Grotesk, body and UI) and `var(--mono)` (data, badges,
identifiers). The two web fonts are loaded per page — see §7.

**Passing a custom property from JS**: `el()` in `core.js` routes any `style` key starting
with `--` through `setProperty()`. `Object.assign(node.style, {'--sys': ...})` does *not*
work — the CSSOM has no setter for custom properties and the declaration is dropped
silently. Do not "simplify" that branch back into an `Object.assign`.

## 7. How a new page works

Pages are static HTML files in the repo root. Each:
1. Links the two Google Fonts (`Instrument+Serif` and `Space+Grotesk`, with the two
   `preconnect` hints above them) and then `assets/css/main.css` (and optionally
   `assets/css/goals.css`). Copy the three `<link>` lines verbatim from `index.html` —
   without them the page falls back to Georgia and a system sans, which is visibly wrong.
2. Has `<header id="site-header">` and `<footer id="site-footer">` — chrome is injected by JS
3. Imports `assets/js/<pagename>.js` as `type="module"`
4. The page JS imports `mountChrome('<activeKey>')` from `core.js` — this renders the header,
   footer, search overlay, and theme/mode toggles

**`activeKey`** must match one of the `matchKey` values in `NAV_GROUPS` in `core.js`:
`overview`, `unified`, `systems`, `goals`, `operations`, `runbook`, `contributing`.

To add a new page to the navigation:
1. Add the page HTML file to the repo root
2. Add a JS module in `assets/js/`
3. Add an entry to `NAV_GROUPS` in `assets/js/core.js` under the appropriate group
   (`Reference`, `State`, or `Meta`) with a new `matchKey`
4. Run `node --check assets/js/core.js` to verify it still parses

## 8. Validation

**Before every commit:**

```
node tools/validate.mjs
```

What it checks:
- All five schemas (`schema/*.schema.json`) against their data files
- Edge endpoints resolve to nodes; flow edges exist
- Task `goal` and `system` references resolve
- Decision system references resolve
- System `status.state` is in `registry.status_vocabulary`
- Section `kind` is in the vocabulary (warn)
- All six required sections present per system (warn)

Exit code 0 = OK (warnings allowed). Exit code 1 = errors, do not commit.

After touching any JS file:
```
node --check assets/js/<file>.js
```

## 9. `data/MASTER-RUNBOOK.md` — do not edit

This file is **generated** by `scripts/sync-runbook-to-hub.sh` in the umbrella repository
(`emmanuelebube13/scalable-brain`). It carries a do-not-edit banner as an HTML comment at
the top. Anything written into it is overwritten by the next sync.

- **You may freely edit** `runbook.html` and `assets/js/runbook.js` — these control how
  the file is rendered (ToC, heading anchors, styling).
- **If you move or rename the file**, you must update `TARGET_REL` in the umbrella repo's
  sync script, or the next sync will recreate the old file at the old path.

## 10. What "done" looks like

A change is done when:
1. `node tools/validate.mjs` exits 0
2. Every touched JS file passes `node --check assets/js/<file>.js`
3. The change is visible on the live site at
   `https://emmanuelebube13.github.io/Scalablebrainfullarchitecture/`
   (allow 20–60 seconds after push for Pages to rebuild)
