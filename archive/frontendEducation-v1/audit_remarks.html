Auditor Remarks: Structural Storage Deficiencies

Detailed verification of findings from the storage assessment, ranked by severity to operational integrity.

1. Unversioned Outcome Overwrites Prevent Past Decision Auditing
Critical Integrity Risk

Audit Finding: In src/outcomes/persist_all.py:55, backtest runs execute ON CONFLICT ("timestamp", asset_id, strategy_id, granularity, leg_index) DO UPDATE SET, and line 390 executes DELETE FROM fact_trade_outcomes WHERE strategy_id = ANY(%s). Backtest outcome rows carry zero run identifier (run_id), no code Git SHA, and no configuration hash.

Auditor Impact: When a strategy backtest is re-run with modified parameters or logic, the old trade history is erased in place. While fact_strategy_regime_attribution preserves run-level metrics per qualification_run_id, the underlying trades that justified past live allocations are permanently lost. For example, Strategy 50's live designation cited 59 OOS trades, whereas today's table contains 191 trades.

-- Prescribed Fix: Append-only run versioning with canonical views ALTER TABLE fact_trade_outcomes ADD COLUMN backtest_run_id UUID REFERENCES dim_backtest_run(run_id); ALTER TABLE fact_trade_outcomes ADD COLUMN code_git_sha VARCHAR(40); CREATE VIEW v_canonical_trade_outcomes AS SELECT DISTINCT ON (strategy_id, asset_id, granularity, "timestamp", leg_index) * FROM fact_trade_outcomes ORDER BY strategy_id, asset_id, granularity, "timestamp", leg_index, created_at DESC;
2. Dual-Identity Tables with Divergent Foreign Key Dependencies
High Architecture Risk

Audit Finding: Strategy identity is duplicated across two 67-row tables: dim_strategy (rich metadata: strategy_key, engine, universe, family) and dim_strategy_registry (thin: strategy_name, is_qualified). Crucially, the foreign keys on fact_trade_outcomes, fact_signals, and fact_live_trades reference dim_strategy_registry rather than the canonical dim_strategy.

Auditor Impact: In dim_strategy_registry, the is_qualified flag is set to true for strategies 17, 22, 26, 41, and 50—yet strategies 26, 41, and 50 failed production gates and are owner-designated. Storing qualification status as a static database flag rather than deriving it from the published regime_strategy_map.json misrepresents production readiness.

3. Strategy Hyperparameters Embedded in Code Rather Than Schema
Medium Maintenance Risk

Audit Finding: Across src/layer0/strategies/**, 125 Python files hardcode strategy parameters (ATR multipliers, indicator lookbacks, stop-loss ratios) directly in class declarations. Although a proper versioned configuration table exists (dim_strategy_config with config_hash, effective_from, effective_to), it contains only 3 rows (strategies 7, 8, 10).

Auditor Impact: Parameter optimization requires a Git commit and code deploy rather than a configuration update, and it is impossible to determine from database records alone which parameter set generated a specific historical trade.

4. Gatekeeper Holdout Leakage Audit Refinement
Confirmed Clean in Trainer

Audit Verification: The initial storage assessment raised a concern that because 40,690 trade outcomes have is_holdout = true and gatekeeper.train.build_frame() does not filter them, the machine learning gatekeeper might be training on untouched holdout data.

Auditor Finding: Detailed code inspection of src/gatekeeper/train.py:run() lines 742–743 proves that the training pipeline explicitly applies: frame = frame[frame["entry_time"] < cut_dt].copy(). Only 101 boundary trades opened before 2023-01-01 and closed after it crossed into the training set. The gatekeeper does NOT train on the 40.6k post-2023 holdout trades.

Schema Hygiene Audit: 6 Dead Tables (0 Rows) & 2 Orphaned Tables Identified
Immediate Cleanup Targets

Auditor Inventory Verification: A full scan of all 24 public relations in ForexBrainDB reveals that 6 tables contain exactly 0 rows (occupying 120 KB of dead disk space and unneeded catalog entries), and 2 tables are severely underutilized / orphaned. These dead relations represent abandoned pipeline branches, legacy schema iterations, and bypassed logging paths:

  • fact_execution_log (0 rows | 16 KB): Designed as a staging table for execution latency and fill telemetry. The production order executor bypasses this table and writes fills directly into fact_live_trades.
  • fact_market_prices_d1 (0 rows | 16 KB): Abandoned daily price partition. Ingestion was refactored into the unified fact_market_prices table with granularity = 'D'.
  • fact_market_prices_h4 (0 rows | 16 KB): Abandoned 4-hour price partition. Ingestion was refactored into fact_market_prices with granularity = 'H4'.
  • fact_market_regime (0 rows | 16 KB): Deprecated v1 market regime store. Superseded by fact_market_regime_v2 (2.56M rows) and fact_regime_structural (2.56M rows).
  • fact_macro_events (0 rows | 24 KB): Economic calendar table created during early architecture planning. No external economic data feed was ever integrated into the pipeline.
  • fact_signal_processing_log (0 rows | 32 KB): Intended for signal generation diagnostics. The active signal pipeline writes diagnostics directly to rotating file streams (signals/YYYY-MM-DD.ndjson).
  • dim_indicator_library (1 row | 48 KB) [ORPHANED]: Contains only a single indicator definition (ATR). All remaining 124 indicators used across the platform are hardcoded in Python code.
  • dim_strategy_config (3 rows | 64 KB) [ORPHANED]: Contains parameter hashes for only 3 strategies (strategies 7, 8, 10). The remaining 64 strategies hardcode their parameters in 125 Python files.

Auditor Recommendation: Execute immediate DROP TABLE operations for the 6 completely dead tables. They have zero active foreign key incoming references, zero application dependencies, and deleting them eliminates developer confusion and catalog bloat.

-- Recommended DDL Cleanup Script (Safe Execution: 0 Rows / No Inward FK Dependencies) BEGIN; DROP TABLE IF EXISTS fact_execution_log; DROP TABLE IF EXISTS fact_market_prices_d1; DROP TABLE IF EXISTS fact_market_prices_h4; DROP TABLE IF EXISTS fact_market_regime; DROP TABLE IF EXISTS fact_macro_events; DROP TABLE IF EXISTS fact_signal_processing_log; COMMIT;

Schema Modeling Analysis: Fact Constellation (Galaxy) vs. Snowflake vs. Star Schema

Rigorous dimensional analysis evaluating how the Scalable Brain PostgreSQL 16 database emulates established data warehouse design patterns, where it diverges, and how relationship arrows govern data integrity.

Architectural Classification: Fact Constellation (Galaxy Schema) with Snowflake Branching
Pattern Verified

A foundational architectural question is whether Scalable Brain's database is a Star Schema, a Snowflake Schema, or a Fact Constellation (Galaxy Schema). Based on rigorous structural and constraint audit across all 24 PostgreSQL tables, the system is classified as follows:

Schema Pattern Theoretical Definition Scalable Brain Implementation Audit Verdict
Star Schema Single centralized fact table surrounded by completely denormalized, single-tier dimension tables. The database maintains 8 independent fact tables across distinct analytical grains rather than a single unified fact table. Furthermore, strategy dimensions are normalized into configs and bridge tables. Not a Star Schema
Fact Constellation
(Galaxy Schema)		 Multiple fact tables sharing common conformed dimensions, allowing cross-fact analytical querying across different business processes. Primary Active Architecture: Central conformed dimensions (dim_asset and dim_strategy) are shared across multiple fact tables: fact_market_prices, fact_regime_structural, fact_trade_outcomes, fact_signals, and fact_live_trades. Primary Architecture
Snowflake Schema Dimensional hierarchy where dimension tables are normalized into sub-dimension levels rather than flattened. Emulated in Strategy Hierarchy: dim_strategy (Master) ──(1:N)──► dim_strategy_config (Parameter Hashes/JSON) ──(1:N)──► dim_strategy_asset_mapping (N:M Bridge) ──(N:1)──► dim_asset. This exhibits textbook snowflake normalization. Snowflake Sub-Branch
Operational 3NF Layer Third Normal Form operational transactional and audit ledger tables outside the analytical OLAP cube. Tables like fact_job_runs (scheduler cron heartbeats), fact_market_prices_quarantine (tick quality filter), and fact_regime_structural_live (streaming live bar buffer) function as transactional operational state. Operational Extension

Auditor Remediation Roadmap

Strategic recommendations to transition Scalable Brain from a single-machine prototype to an institutional multi-run quantitative research and execution platform.

1. Outcome Provenance

  • Create dim_backtest_run table recording run UUID, code commit SHA, and timestamp.
  • Add run_id and config_hash to fact_trade_outcomes.
  • Stop destructive DELETE and DO UPDATE in backtest writers.
  • Deploy v_canonical_trade_outcomes view for legacy pipeline readers.

2. Identity Consolidation

  • Merge dim_strategy_registry into dim_strategy.
  • Repoint foreign keys on fact_trade_outcomes, fact_signals, and fact_live_trades.
  • Deprecate is_qualified boolean; replace with dynamic map resolution.
  • Key strategy-notes.json by stable strategy_key.

3. Metric Hygiene & Config

  • Relabel fact_strategy_regime_attribution.avg_r to payoff_ratio to prevent misinterpretation.
  • Extract hardcoded parameters from the 125 Python files into versioned JSON configs synced to dim_strategy_config.
  • Flatten src/layer0/strategies/ folders and track lifecycle status via database enums.
