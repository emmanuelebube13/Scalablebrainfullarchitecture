Multi-agent content layer

Editing this site

Nothing on this site is written in HTML. Every page fetches structured JSON from data/ and renders it. A human, a script or an automated agent changes what the site says by committing a JSON change — never by touching markup.

If a change requires editing an HTML file, either the schema is missing something or the change is a design change. Those are different problems and they have different reviewers.
Layout

Where everything lives

Five content files and one template. That is the whole editable surface.

data/
├── registry.json            Project identity, principles, and the list of systems
├── architecture.json        Nodes, edges and traceable flows for the unified map
├── decisions.json           Architecture decision records — including open ones
├── goals.json               Milestone ladder, goals, dependency matrix, task tracker
└── systems/
    ├── system-1.json        One file per subsystem, all sharing one schema
    ├── system-2.json
    └── system-3.json

schema/                      JSON Schema for each of the above — validate before committing
templates/
└── system.template.json     Copy this to add System 4
tools/validate.mjs           Zero-dependency validator: node tools/validate.mjs
assets/                      Stylesheet and ES modules. Design, not content.

The one rule

Content lives in data/. Presentation lives in assets/. An agent updating a status, adding a task or documenting a new pipeline stage should only ever touch data/.

Conventions

Two rules that make the content usable

Every explanation comes in two voices

Anywhere the schema allows an explanation, it takes an object with technical and plain keys. The header toggle picks one. Writing only technical is allowed and falls back gracefully — but the plain version is where most of the value is, because it is the one a non-engineer can challenge you on.

"summary": {
  "technical": "4-state Gaussian HMM on D1/H4/H1 with K-Means fallback below a 0.70 accuracy gate.",
  "plain": "Sorts market history into four kinds of weather, and falls back to a simpler
            method if it cannot do that reliably."
}

Light inline markup, deliberately not Markdown

Strings support `code`, **bold**, *italic* and [label](https://…). Everything is HTML-escaped first, so content written by an agent cannot inject markup into the page. If you need a table, use a tables entry rather than hand-drawing one in a string.

Workflow A

Editing through Git

The normal path for a developer or an agent with a checkout.

  1. Clone and branch

    git clone https://github.com/emmanuelebube13/Scalablebrainfullarchitecture.git
cd Scalablebrainfullarchitecture
git checkout -b update/system-1-status

  2. Edit the JSON

    Change only what you mean to change. Statuses, metrics and task rows are the common edits; structural changes to the schema are not.

  3. Validate before committing

    The validator has no dependencies and needs no install. It checks every content file against its schema and cross-checks referential integrity — every edge endpoint resolving to a node, every flow edge existing, every task pointing at a real goal and a real system.

    node tools/validate.mjs

  4. Preview locally

    The pages load their content with fetch(), which browsers block on file://. Serve the folder over HTTP:

    python3 -m http.server 8080
# then open http://localhost:8080

  5. Commit and push

    One logical change per commit, with a message stating what became true — not what file moved. GitHub Pages redeploys from the default branch automatically.

    git commit -am "S1: producer repaired (FIX-S1-016); cadence still daily"
git push -u origin update/system-1-status
Workflow B

Editing through the GitHub API

For automated agents with no checkout — a CI job, a monitoring script, or a system on another computer reporting its own status.

Read the current content and its blob SHA

curl -s -H "Authorization: Bearer $GITHUB_TOKEN" \
  -H "Accept: application/vnd.github+json" \
  https://api.github.com/repos/emmanuelebube13/Scalablebrainfullarchitecture/contents/data/goals.json \
  | jq -r '{sha, content}'

Write it back

The sha is required and acts as optimistic concurrency control: if another agent has committed since you read, your write is rejected rather than silently overwriting them. Re-read and re-apply.

NEW_CONTENT=$(base64 -w0 goals.json)

curl -s -X PUT \
  -H "Authorization: Bearer $GITHUB_TOKEN" \
  -H "Accept: application/vnd.github+json" \
  https://api.github.com/repos/emmanuelebube13/Scalablebrainfullarchitecture/contents/data/goals.json \
  -d @- <<JSON
{
  "message": "S3: confirm subscription name on Scored_Signal_Queue",
  "content": "$NEW_CONTENT",
  "sha": "$CURRENT_SHA",
  "branch": "main"
}
JSON

Concurrency is the failure mode to design for

Three systems on three computers writing one file will collide. Two mitigations, in order of preference: have each system own a distinct file or a distinct array (System 3 only ever appends tasks whose id starts T-3), and always send the sha you read so a collision is an error rather than a silent loss.

Read-only consumption

Any system can consume this content without credentials — the raw files are public and CORS-enabled, which makes them a legitimate integration point rather than only a website:

curl -s https://raw.githubusercontent.com/emmanuelebube13/Scalablebrainfullarchitecture/main/data/goals.json \
  | jq '.tasks[] | select(.system=="system-2" and .status!="done")'
Extensibility

Adding System 4

The site is built for N systems. Adding one is a data change, and no HTML, CSS or JavaScript is touched.

  1. Copy the template

    cp templates/system.template.json data/systems/system-4.json

    Fill in id, ordinal, name, role, host, accent, the two-voice summary, and as many sections as you have content for. Sections are rendered generically — body, stages, tables, callouts and issues all render wherever they appear.

  2. Register it

    Append one entry to systems in data/registry.json. The overview page, the subsystem navigation, the goal filters and the dependency matrix all pick it up from there.

    { "id": "system-4", "ordinal": 4, "file": "data/systems/system-4.json" }

  3. Put it on the map

    Add a column to columns in data/architecture.json, then nodes that reference it. Nodes declare a column and a row; coordinates are computed, so there is no pixel arithmetic and no layout to rebalance.

    { "id": "s4", "title": "System 4 — The Analyst", "system": "system-4",
  "subtitle": "Computer 4 · nightly" }

{ "id": "s4-report", "column": "s4", "row": 2, "label": "Report builder",
  "kind": "process", "status": "planned",
  "detail": { "technical": "…", "plain": "…" } }

  4. Wire its dependencies

    Add a { "system": "system-4", "role": …, "need": … } entry to any goal in data/goals.json that it touches. The dependency matrix is generated from those arrays, so it cannot drift from the goals themselves.

  5. Validate and push

    node tools/validate.mjs && git commit -am "Add System 4 — The Analyst"
