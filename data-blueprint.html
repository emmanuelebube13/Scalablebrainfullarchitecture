Data Blueprint

Four views of the same system. The conceptual model says what the business things are and how they relate, with no tables and no technology. The data flow diagrams say where data enters, which program moves it and where it rests today. The logical model gives each thing one owning store, with keys and history rules. The physical model shows the tables now built in production.

Data flow, context

One PC holds everything. The practice broker account is the only place orders go. Two outputs are meant to exist and do not work yet, and two kinds of account are not connected.

Data flow, level 1, as it runs today

Signals from two producers meet on one queue. Guardian, the bridge and Hand pass orders and fills over that same queue, and only Hand talks to the broker. Everything below the trade path is copying and watching.

Logical model

The conceptual things now have one owning store each, with keys and history rules. Four new schemas in the existing PostgreSQL database hold them: config, trading, finance and ops. Price bars, regimes, research and external data stay where they are. Rows are keyed by business keys, every time is a UTC instant, and every trading, finance and ops row names its instance.

For risk decisions, orders and trades, the producer's own journal stays as the working copy. The business record is the PostgreSQL table, and one relay is its only writer. If they disagree, the journal is corrected through an audited command and the relay re-syncs.

How a setting reaches the trade path

What stays in code

  • Wire contracts (signal, order, fill, account snapshot, command) change only with the code that reads them.
  • The order and meaning of the Guardian's gate layers is code. Every threshold inside it is a setting.
  • Sizing arithmetic and rounding are code. Risk percentages and multipliers are settings.
  • Broker binding: host, account kind and account id must agree, with exactly one credential set. A live instance will not boot without the owner's mode file.
  • Order idempotency: a client id, reconcile before create, and an order that cannot be verified counts as already sent.
  • The STOP sentinel is absolute. Breakers latch until an operator resets them.
  • No default instance: a message or row with no instance key is refused.
  • The trade path cannot read the finance schema, so a goal can never loosen risk.
  • Ledgers are append-only by trigger. Settings-unavailable behaviour and the snapshot hash check are code, not settings.

Roles and grants

The design has four database roles: an app role for the dashboard and control panel, a relay role for the writers, a research role, and a read-only role for analysis. Migration 021 creates them. It has not been applied in production, because creating roles needs the superuser password. Until then every new job connects as sa. The trade path has no database login in scalable_brain at all.

Service-private stores (SQLite)

  • ams.db: Guardian journal. Gains instance_key on every table, settings_version and constraints_checked on decisions, and a new instance-day table. The two strategy control tables are retired as sources.
  • system2.db: Hand's order record. Gains instance_key, execution_mode and settings_version; the relay becomes its first reader.
  • queue.db: The message queue. One file per instance; a service refuses a queue that belongs to another instance. It is transport only.
  • fill_outbox.db, processed.db, close_sweep.db: Move into each instance's own folder. Schema unchanged.
  • equity_history.db, notifications.db, shadow_incubator.db: Retired after their data is copied into PostgreSQL.

Questions for the reviewer

  1. Are these the right 24 business things, and is anything missing or split wrongly?
  2. Should a signal belong to a strategy version, so that every trade can be traced to exact code and parameters?
  3. Should account and environment be plain attributes, so that a live or prop-firm account is one more row?
  4. Which store should own each thing? The trade and the strategy are the two with the most copies today.
  5. Should the dashboard read the owning store directly and show the age of every copy it relies on?
