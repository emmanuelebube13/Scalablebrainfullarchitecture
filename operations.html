2. SQL Templates for Fact_Market_Prices

Run these in pgAdmin to verify and analyze the price data.

Check Latest Ingested Data per Timeframe

SELECT 
    a."Symbol", 
    p."Granularity", 
    MAX(p."Timestamp") as latest_candle_time,
    COUNT(*) as total_candles
FROM "Fact_Market_Prices" p
JOIN "Dim_Asset" a ON p."Asset_ID" = a."Asset_ID"
-- Uncomment to filter by granularity:
-- WHERE p."Granularity" = 'M30'
GROUP BY a."Symbol", p."Granularity"
ORDER BY a."Symbol", p."Granularity";

View the Most Recent 100 Candles for an Asset

SELECT 
    a."Symbol", 
    p."Granularity", 
    p."Timestamp", 
    p."Close", 
    p."Volume"
FROM "Fact_Market_Prices" p
JOIN "Dim_Asset" a ON p."Asset_ID" = a."Asset_ID"
WHERE a."Symbol" = 'EUR_USD' AND p."Granularity" = 'H1'
ORDER BY p."Timestamp" DESC
LIMIT 100;

3. Deploying to trading-1

The single most important fact: /opt/scalablebrain on the VM is not a git checkout. It has no .git, no remote, and there is no deploy script. It is a separate copy updated by hand, file by file. Editing the repository therefore changes nothing in production, and restarting a service afterwards restarts the old code while looking like a successful deploy.

This has already happened. On 2026-08-29 seven System 3 endpoints were implemented, the repo was edited, s3-ams and telemetry-pub were restarted, and the work was reported as shipped. All seven were still returning 404. The restart interrupted the live gate for no benefit.

“I restarted the service” is not evidence. “I called the endpoint and got the expected value” is.

The repo and production diverge in both directions

Neither side is globally newer, so there is no safe general rule — diff before every copy. Measured 2026-08-29:

FileRelationship to production
system3/ams/src/ams/service/api.pywas identical before the change
system2/…/execution/lifecycle.pyrepo ahead — carries shadow_fn
bridge/telemetry_publisher.pyrepo ahead ~322 lines of unrelated work
bridge/ops_watchdog.pyproduction is ahead of the repo

Two outages, one cause

A file can be in sync while its collaborators are not. Check what the file calls, not just the file.

  • 2026-08-28 — lifecycle.py. Copied wholesale, it passed shadow_fn= to a HealthReporter that production does not accept. System 2 crash-looped for ~2 minutes.
  • 2026-08-29 — api.py. The file itself was in sync and syntax-clean, but it called source.producer_liveness(), which production’s Service lacks and its build_health does not accept. /health returned 500, which also blinds the ops watchdog’s heartbeat check. Rolled back in under a minute, fixed to probe both sides, redeployed.

Procedure

StepCommand / check
1. Diff against production gcloud compute ssh trading-1 --zone europe-west1-b --tunnel-through-iap --command='cat /opt/scalablebrain/<path>'
2. Separate your change from pre-existing divergence git -C <nested repo> show HEAD~1:<path> | diff - prod_file.py — if non-empty, splice onto the production file, do not copy
3. Check the collaborators, in the service’s own venv sudo -u trader ./.venv/bin/python -c "import inspect; from ams.service.health import build_health; print(sorted(inspect.signature(build_health).parameters))"
4. Back up with checksums BK=/opt/scalablebrain/backups/<name>-$(date -u +%Y%m%dT%H%M%SZ), then md5sum * > MD5SUMS.before
5. Syntax-check on the VM python3 -c "import ast; ast.parse(open('/tmp/incoming.py').read())" — not py_compile, which fails on __pycache__ permissions
6. Install and restart sudo install -o trader -g trader -m 644 /tmp/incoming.py <prod path> then sudo systemctl restart <units>
7. Verify behaviour, not liveness NRestarts must be 0 — active alone does not rule out a crash loop. Then call the endpoint and compare to source of truth.
8. Rollback sudo install -o trader -g trader -m 644 "$BK/<file>" <prod path> then restart

Units are system2, s3-ams, s2s3-bridge, s3-signal-relay, telemetry-pub — note it is s3-ams, not system3-ams. System 2 is :8002, System 3 is :8300. Restarting system2 or s3-ams interrupts live execution: get approval, and prefer a market-closed window (forex closes Friday ~21:00 UTC).

The dashboard is a different path entirely. It does not live on trading-1. It is Cloud Run service telemetry-dashboard (europe-west1), built from telemetry-dashboard/ and shipped as a new revision. The VM’s copy under /opt/scalablebrain/telemetry-dashboard is a stale leftover — do not deploy to it.

Standing invariant: nothing in any deploy may set go_live_enabled or flip mode to enforce. These surfaces report state; they must never be the thing that turns live trading on.
