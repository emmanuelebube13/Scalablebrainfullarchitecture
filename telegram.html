Telegram Commands

Every command available to operators via the Telegram bot interface. Commands interact directly with the live risk engine — state changes, circuit breaker resets, and manual overrides.

All destructive commands require a two-step CONFIRM. The system audits every attempt — confirmed or not.
Protocol

How Commands Work

Commands follow a consistent two-step pattern for anything destructive. All attempts are written to override_audit regardless of outcome.

  1. Send the command

    Type /command_name [args]. The bot replies with a preview of what will happen and a 60-second confirmation window opens.

  2. Confirm within 60 seconds

    Send /command_name [args] CONFIRM to execute. If you miss the window, send the command again to start fresh.

  3. Read the result

    Every executed command replies with what changed. Check /status after any state-changing command to verify the live system reflects the intent.

CLI one-shot

From the server you can run ams.ctl <command> CONFIRM directly without the two-step — the CLI treats an explicit CONFIRM argument as the deliberate second factor.

State control

Trading Control

Commands that pause, resume, or forcibly flatten all open positions.

Command Effect Confirm?
/pause Moves the account to PAUSED state immediately. No new trades are approved. Existing open positions are left untouched. Can be sent from ACTIVE, CAUTION, DEMO, or RECOVERY. No
/resume CONFIRM Moves from PAUSED back to the state that was active before the pause. Only valid from PAUSED — refused from any other state. Yes
/flatten CONFIRM Publishes a flatten_all command to System 2 (closes every open position) and moves the account to PAUSED. Preview shows open position count and total unrealized P&L before you confirm. Yes

/flatten is irreversible

Once confirmed, the flatten command is on the wire to System 2. There is no recall. Use /status first to see exactly what is open and the current P&L before confirming.

Risk overrides

Circuit Breaker Control

Circuit breakers fire automatically on risk thresholds. These commands let you inspect and manually clear them.

Active breaker names

Pass the exact breaker name (shown in /status and in CRITICAL alerts) to /reset_breaker.

Breaker name Fires when Severity Auto effect
max_drawdown Equity drops ≥ 20% from peak 100 — Hard Flatten all → CIRCUIT_BROKEN
weekly_loss Weekly loss ≥ 6% of equity 80 Halt rest of ISO week; next-week risk cap 0.5%
hard_daily_loss Daily loss ≥ 3% of equity 70 Halt new trades for 24 h
consecutive_losses 5 losing trades in a row 60 Halt new trades for 24 h
margin_act Margin level ≤ 120% 55 Close largest losing position
margin_warn Margin level ≤ 150% 40 — Alert only Alert only, no trade action
soft_daily_loss Daily loss ≥ 2% of equity 30 Size −50%, 30-minute pause
correlation_shock Correlated group loss ≥ 10% equity 25 Close the correlation group
volatility_spike Realized vol > 2σ of rolling window 20 Size −50% platform-wide

Reset command

Command Effect Confirm?
/reset_breaker <name> CONFIRM Clears the named breaker's active log row. Restores size_multiplier to 1.0 and clears halted_until in risk_state (only when no other breakers remain active). Auto-acknowledges the associated CRITICAL alert so it stops re-paging. If the account is in CIRCUIT_BROKEN state (triggered only by max_drawdown), the reset additionally moves it to RECOVERY. Yes

What reset does NOT do

Resetting a breaker clears the halt timer and the log row. It does not reset the underlying counter (e.g. consecutive_losses in ams_account_state). That counter only clears when a winning trade closes. If the next trade loses, the breaker fires again immediately.

Example usage

# Step 1 — preview
/reset_breaker consecutive_losses

# Bot replies with preview. Within 60 seconds:
/reset_breaker consecutive_losses CONFIRM

# Bot replies: Breaker 'consecutive_losses' reset.
# CLI one-shot (from server)
ams.ctl reset_breaker consecutive_losses CONFIRM
Recovery

Recovery & Stage Management

After a hard circuit break the account passes through a RECOVERY probation state before returning to full size. These commands manage that path.

Command Effect When valid Confirm?
/clear_recovery CONFIRM Moves from RECOVERY → ACTIVE. Trading continues at the recovery_max_risk_pct cap (0.5%) until this is called. Only from RECOVERY state Yes
/stage_up CONFIRM Advances the deployment stage ladder (paper → micro → small → full). Eligibility is re-evaluated at confirm time — refused with unmet criteria listed if the ladder conditions are not met. Any trading state Yes

State machine path after a hard break

CIRCUIT_BROKEN → /reset_breaker max_drawdown CONFIRM → RECOVERY → /clear_recovery CONFIRM → ACTIVE

Gate mode & alerts

Mode Control & Alert Acknowledgement

Command Effect Confirm?
/mode shadow Gate approves and logs decisions but does not publish orders to System 2. The safe direction — no confirmation required. No
/mode enforce CONFIRM Gate publishes live orders to System 2. Requires the go-live checklist flag to be set — refused until Task 20 has been completed and the flag is explicitly enabled. Survives service restarts (persisted in DB). Yes
/ack Acknowledges all unacknowledged CRITICAL alerts, stopping repeat pages. Individual breaker alerts are auto-acknowledged by /reset_breaker — use /ack for anything else. No
Strategy management

Strategy Quarantine

The decay auditor (Task 16) can bench a strategy if its live performance diverges too far from the backtest baseline. These commands manage that.

Command Effect Confirm?
/unquarantine <strategy_id> CONFIRM Clears the quarantine flag on a strategy, setting its status back to active. Signals from that strategy will pass Gate Q again. Only do this after reviewing the decay audit — the gate will not block you, but the audit reason is still there. Yes
